## Implemented foundation

Packaged renderer URLs use the resolved installation path and proper file-URL encoding; equivalent filesystem aliases must resolve to the exact renderer file, while other files, remote URLs and query strings remain rejected. Installer startup failures report the application path and renderer URL for diagnosis.
- A database utility host with SQLite workspace storage; user SQLite connections execute in isolated child processes. The renderer receives no Node, shell, generic filesystem, or credential-reading API.
- Locally bundled Monaco SQL editor with selection or script execution, native SQL file open/save, and command palette.
- Versioned SQLite recovery of multiple SQL buffers and saved non-secret connection profiles, bounded local query history, and history clearing.
- Desktop packaging configuration for macOS, Windows, and Linux.
- Docker Compose PostgreSQL 17, MySQL 8.4, MariaDB 11.4, SQL Server 2022 Developer and Oracle Free 23.26.3 fixtures with generated TLS certificates and sample relational data.

## Implemented profiles and query tabs

- Create, edit, delete and reopen named connection profiles for every adapter. Save profiles independently or while connecting. Passwords remain in memory by default, with optional OS-store persistence described below. Access tokens remain session-only; strict workspace validation rejects secret fields and live runtime state.
- Up to 20 query tabs, each with a dedicated session, SQL buffer/Monaco model, undo and cursor state, explorer/filter, current result selection, messages, timing, cancellation and transaction status. Different tabs execute concurrently, including across engines. Tabs sharing a database retain ordinary server locking and committed-data visibility.
- New tabs can reuse a live tab's credentials to open another physical connection. Saved server profiles accept an explicit password or use an opted-in OS-store entry; saved embedded profiles connect directly. Profile edits never retarget an existing connection. Deletion detaches open tabs while preserving their settings and sessions.
- Execution UUIDs are assigned before IPC and events must match both session and execution. Background completion cannot replace the active tab's results or transaction badge. The registry and each adapter keep one fetched-result cache per session, removing it on that session's next execution or disconnect.
- Close guards cover connecting/running tabs and every non-idle transaction state, with explicit confirmation before discarding a buffer. Normal quit checks all tabs, offers a keep-working choice, and requests a final workspace flush before ending sessions. A failed flush is reported instead of silently discarding the latest changes.
- Workspace version 2 stores ordered tabs, active tab ID and up to 100 profiles. A transactional v1 migration preserves the original scratch SQL/profile and history, creates a standalone WAL-aware SQLite backup, and rejects newer or invalid formats. Recovered tabs stay disconnected; neither SQL nor transactions are replayed.
- Session loss clears only its owning tab. Database-host or renderer loss ends all live sessions; saved tabs survive. Results and live credentials are not restored; opted-in passwords require an explicit connection request. SQLite cancellation still ends only the cancelled tab's worker.

## Implemented SQL language tools

- Per-tab schema snapshots with catalog/schema/table/view identity, ordered columns, type names and nullability. Typed, sender-validated `schema` IPC runs through the production registry. Metadata is not a user execution and never overwrites query results, export caches or history.
- Server metadata uses independent connections to preserve the live query transaction and avoid changing its diagnostics; catalog statements have bounded results and ten-second execution/connection-close timeouts after connecting. SQLite/DuckDB reserve the owning idle session, preserving local and attached object visibility. UI query/connection controls wait while a refresh is active.
- Snapshots are fetched on connect, explicit refresh and after schema/context/transaction-changing execution. They are ephemeral, scoped by session ID, cleared on loss/disconnect, and capped at 2,000 objects / 10,000 column rows. The sidebar shows failures and truncation. Typing and formatting do not call the database.
- Monaco completion handles dialect quoting, alias-qualified columns, schema/catalog-qualified tables, basic joins, statement/subquery boundaries, simple CTE projections, keywords and common dialect functions. Comments and literals suppress suggestions. Requests bind to the model URI, version and schema context; late responses cannot edit another tab.
- Pinned `sql-formatter` 15.9.0 with explicit PostgreSQL/MySQL/MariaDB/T-SQL/SQLite/Oracle/DuckDB dialect imports; Azure SQL uses T-SQL. Document and range providers, toolbar, command palette, context menu and Shift+Alt+F integrate with Monaco's undo stack. Formatting preserves case, comments/literals/identifiers and client GO repeat lines; token changes are refused. Unsupported procedural/DELIMITER scripts produce an error with no edit.
- A bundled language Web Worker keeps parsing/formatting outside the UI thread. Inputs are limited to 200,000 SQL characters, completions to 200 items, and each worker request to three seconds. Cancellation/version checks discard obsolete results; an unresponsive worker is terminated and recreated with the current contexts.
- Shared Docker contracts validate real schema discovery, generated quoted completions executed by each engine, equivalent results before/after formatting, DDL refresh, transaction preservation and embedded-session isolation. SQL Server also includes an Azure-profile contract. Real Electron workflows exercise suggestion acceptance, document/range formatting, undo, failure preservation and tab isolation; packaged DuckDB coverage is part of the three-OS smoke script.

## Implemented SQLite workflow

- SQLite appears alongside the server engines, with native open/create file dialogs and no network or password fields. Existing writable/read-only files, exclusive new-file creation and per-connection in-memory databases are supported. Saved create profiles become ordinary open profiles for the next connection.
- The production driver uses `node:sqlite` in a separate child process for each retained connection. Electron 44.7.0 provides Node 24.21.0 / SQLite 3.53.4 on the verified Mac; the Docker runner pins the same Node release. No new native addon or external SQLite executable is required. The worker requires Node 24.10+ for the public authorizer API.
- SQLite `prepare()` / `sourceSQL` determine exact statement boundaries. Triggers, quoted semicolons, CASE expressions, CTEs, multiple results, PRAGMAs and DML `RETURNING` run without SQL rewriting. A script stops after the first error. At most 200 statements execute; crossing that limit fails after earlier statements may have completed. Unbound placeholders are rejected before any statement runs.
- Results preserve ordinal columns, signed 64-bit integers, raw text, blobs as hex, Unicode, NULL and empty strings. SQLite REAL values retain SQLite's floating-point semantics; NUMERIC affinity is not an arbitrary-precision decimal guarantee. Row/byte caps and acknowledgements bound retained previews; excess rows are drained so DML completion is not cut off by the preview cap.
- Transaction status comes from `DatabaseSync.isTransaction`, including outer SAVEPOINTs, failed deferred-constraint COMMITs and `ON CONFLICT ROLLBACK`. No SQL-keyword approximation is used. Temporary tables and attached databases belong to the retained connection; metadata is bounded and uses that connection while idle.
- File read-only mode combines the native read-only open flag, query-only mode and an authorizer preventing ATTACH and disabling query-only mode. File creation is exclusive. Foreign keys default on, double-quoted string literals and extension loading are disabled, and lock waits initially time out after one second. File encryption/SQLCipher is not implemented.
- Stop forcefully ends only that SQLite child. It reports an unknown in-flight outcome and requires reconnect; it does not claim to undo previously committed statements. Temporary state is lost. A separate watchdog thread detects a dead owner even while the native query blocks JavaScript, then exits the child so journal recovery can release transactions/locks. Renderer-crash recovery tests verify that no orphan retains a write lock.
- Docker executes real-file tests through the same driver registry and worker code. Native Electron tests cover dialogs, catalog SQL, exact values, CSV, rollback, read-only enforcement, Stop, reconnect, renderer crash and restart. The packaged smoke check also starts the real SQLite child from the shipped application.

## Implemented Oracle workflow

- `oracledb` 26.0.0, pinned in Thin mode without native install scripts or Oracle Client libraries. One standalone physical connection per query tab; explicit reconnect only, no retry/replay. Service-name/password connections support TCP or TCPS with strict hostname and certificate-chain checks.
- Oracle TLS uses runtime trust roots, including `NODE_EXTRA_CA_CERTS` configured before application startup. The dialog hides the custom CA field for Oracle and the driver rejects nonempty values rather than silently ignoring them. No global TLS patches or disabled certificate verification are used. Wallet/mTLS, SID/TNS aliases, privileged roles and cloud IAM are not exposed yet.
- SQL scripts, q/nq quoting, PL/SQL anonymous blocks and stored units separated by standalone slash lines. A final PL/SQL block may omit `/`. SQL*Plus commands and unbound client parameters fail preflight. Trigger `:NEW`/`:OLD`/`:PARENT` correlation names are allowed; custom correlation aliases and inline WITH PL/SQL declarations are not supported.
- Cursor results, ordered PL/SQL implicit results, duplicate names, affected rows, compile warnings and DBMS_OUTPUT messages. Previews retain at most 1,000 rows per set / 8 MiB per execution. LOB reads are bounded before allocation; a row that exceeds the byte budget is omitted and truncation is explicit. SELECT cursors close at the cap instead of draining unbounded results, and their total row count is unknown. Arbitrary user SQL/functions may still do server work before rows arrive.
- NUMBER and native JSON fetch as server-produced text, avoiding JavaScript numeric rounding. DATE/TIMESTAMP/TIMESTAMP WITH TIME ZONE use an isolated, per-connection TTC decoder hook because Thin mode converts even STRING requests through lossy JavaScript Dates. The hook preserves nine-digit fractions and years 1–99, independent of local timezone/NLS settings. Fixed offsets are preserved; named-region timestamps and LTZ display exact UTC instants. LTZ with a named DBTIMEZONE requires explicit TO_CHAR conversion. Initial session timezone is UTC; users can change it. RAW/BLOB display as hex, CLOB/NCLOB as text, and empty Oracle strings remain NULL. Complex objects, vectors and external BFILE values require explicit SQL conversion; they are not silently rounded or stringified.
- Manual commit mode, native `transactionInProgress` state, savepoints, commit/rollback and implicit DDL commits. Begin creates `SAVEPOINT DBCOMMANDER_BEGIN`. Ordinary Oracle statement errors leave preceding work available for commit/rollback. Disconnect guards remain active for running queries and open transactions.
- Native `connection.break()` cancellation is acknowledged before session reuse and prevents later script statements. Server calls that do not poll in-band breaks, such as DBMS_SESSION.SLEEP in this fixture, may not acknowledge Stop until they return. A bounded ping detects lost connections at execution completion, reporting unknown outcomes and requiring explicit reconnect. Metadata uses a separate connection and lists at most 2,000 login-schema tables/views; temporary table definitions are visible, console-local rows are not.
- Oracle 26ai Free 23.26.3 Docker fixture with pinned multiarchitecture image digests, generated wallet, verified TCPS and explicit TCP. The same driver registry is exercised by integration contracts and an Electron workflow; Oracle has its own Ubuntu CI matrix job.

## Implemented DuckDB workflow

- Official `@duckdb/node-api` 1.5.6-r.1 and native DuckDB 1.5.6, using its public asynchronous API inside the database utility process. Native crashes are contained by the existing host-loss/reconnect path. There are no private parser/decoder patches.
- Open existing, read-only, exclusive new-file creation and isolated in-memory modes, with native file dialogs and recoverable profiles. New databases are initialized privately, closed, and atomically hard-linked into place without overwriting an existing target; filesystems without hard-link support fail creation explicitly. New files have mode 0600 where supported. Only absolute regular-file paths are accepted outside memory mode.
- Retained connections share reference-counted instances by exact device/inode identity, including aliases. Access-mode conflicts fail explicitly. Native file locks reject other writer processes. Connection-local temp tables and variables survive query runs. Initial engine settings are 512 MB and four threads per instance, configurable through SQL; these are not a total process-memory bound.
- Native extraction parses the complete script before executing up to 200 statements sequentially. Syntax errors prevent execution; a bind/execution error stops at that statement. Prepared parameters are rejected when reached, so earlier successful statements can remain committed. Multi-statement result labels identify the native command and ordinal; the history retains original SQL.
- Exact value classes preserve HUGEINT/UBIGINT, decimals and nanosecond timestamps, including nested values. Blobs display hex. Duplicate column names retain ordinal values. Native result metadata supplies type names and DML counts.
- Streams use bounded chunks and renderer acknowledgements, retain at most 1,000 rows per result in the UI and 8 MiB per execution, and drain omitted rows to finish mutations and report counts. The limits do not bound query work, total native memory or a single large value/chunk. CSV exports cached rows without replay.
- Begin/commit/rollback and failed-transaction controls use two system-qualified transaction-ID queries at execution completion: same ID means an explicit transaction, differing IDs mean autocommit, and the engine's aborted-transaction error means rollback is needed. Other probe errors produce unknown state. Probes are intentionally not placed between script statements; inspect last-query diagnostics within the script.
- Native `interrupt()` runs only while an application query call is pending. Stop also ends the remaining script at backpressure boundaries without interrupting an idle connection/state probe. Transactions are left in the engine-reported state; rollback is explicit. Closing the driver interrupts active work and disconnects, rolling back uncommitted writes.
- Explorer lists up to 2,000 tables/views across catalogs and schemas, including session-local and attached objects. Generated previews quote all three identifier components. Metadata runs on the retained idle connection, so uncommitted schema changes are visible; concurrent refresh/execution is rejected.
- Local CSV/Parquet queries and COPY use the actual embedded engine. Read-only protects the selected catalog, not the filesystem. Automatic extension installation/loading is initially disabled; explicit signed extensions and SQL opt-in remain available. There is no extension management UI, parameter prompting or MotherDuck/cloud credential workflow yet.
- Docker native-engine contracts, an Electron workflow, native x64 CI matrix entry, and packaged SQLite/DuckDB smoke tests across the three OS build jobs. The platform addon and companion library are automatically unpacked from ASAR with their upstream license.

## Deliberate limitations and next work

1. SQL Server/Azure SQL adapters passed the native x64 baseline in Azure run 278; separate live Azure certification remains pending. SQLite, Oracle and DuckDB are implemented; later engines remain planned. Later milestones list their own validation results below.
2. Tabs have independent physical sessions but share one database utility host (SQLite additionally has one child process per session). Per-profile host processes and split panes remain planned. Connection organization and tab reordering are implemented in later sections; reordering runtime validation is deferred. The preview caps sessions/tabs at 20, profiles at 100 and total recovered SQL at five million characters (one million per tab).
3. Editable base-table pages support staged insert/update/delete, parameterized SQL previews and original-value concurrency checks. A strictly eligible `SELECT * FROM schema.table` result can open a fresh source-table edit page; arbitrary SQL results remain read-only. Editing requires a primary key, supported columns and a fresh transaction per batch. Server-side table/view pagination, filters and sorting are implemented below. Key changes and unsupported binary/LOB/complex types require SQL.
4. Each tab retains at most 1,000 rows per result set and 8 MiB of text for its latest execution in both the renderer and export cache; totals grow with the number of tabs, and these text caps are not total process-memory caps. These limits do not bound server work. MySQL/MariaDB/SQL Server/SQLite/DuckDB drain rows beyond the preview limit without retaining them, so execution time/network traffic remain unbounded until completion or cancellation. Most adapters must still receive a single large value; Oracle bounds LOB reads before allocation and closes truncated cursors. A general lazy large-object viewer is not implemented. Only the first 100 columns are rendered; fetched CSV includes all columns.
5. CSV exports fetched rows. Full-result export/import UI, spreadsheet-safe formula conversion, JSON/Parquet export UI, and PostgreSQL COPY streaming remain planned. DuckDB can already read/write local CSV and Parquet through SQL. CSV preserves raw values; spreadsheet applications may interpret formula-looking text.
6. PostgreSQL COPY and psql meta-commands are unsupported. The lexical splitter handles common PostgreSQL syntax but not every procedural construct, including SQL-standard BEGIN ATOMIC bodies. PostgreSQL session changes to string-escaping rules are not supported by its splitter. MySQL/MariaDB SQL_MODE changes must run separately; subsequent executions respect NO_BACKSLASH_ESCAPES and ANSI_QUOTES. Client commands other than DELIMITER, client-side parameter prompts, and interactive LOCAL INFILE are not supported. MariaDB Oracle-mode procedural syntax is not certified.
7. Schema completion and SQL formatting are implemented, with deliberate limits: no full semantic SQL validation, arbitrary derived-table/correlated-query inference or stored-procedure argument discovery. Server snapshots exclude local temporary objects and uncommitted DDL because they use separate connections; Oracle currently lists only the login user’s objects. Parameter prompts remain planned; subsequent sections document query-plan visualization and schema designers. Procedural bodies and DELIMITER scripts must be excluded from formatting selections.
8. Optional OS-store password persistence is implemented below. SSH, interactive Azure authentication/token renewal, integrated authentication, and protected production profiles remain planned. SQL Server endpoints use an explicit host and TCP port; named-instance browser discovery is not implemented.
9. Workspace storage runs in the utility process using Node's bundled `node:sqlite`, avoiding a native addon rebuild. User SQLite databases have their own isolated child processes. It is experimental in the supported Node 22 development runtime. Test the bundled Electron runtime on every release platform. Schema version 2 rejects newer files and backs up version 1 before migration. SQL text, profile endpoints and history are unencrypted, including migration backups.
10. Updaters, signing/notarization, crash uploads, telemetry, and public extensions are not enabled. Do not describe development packages as signed or production-certified.
11. The shipped UI is dark themed. Full accessibility certification, light/high-contrast themes, shortcut customization, and localization are follow-up work.
12. The packaged renderer uses a local file URL with strict sender validation. Migration to a dedicated application protocol and Electron fuse hardening are planned before a stable release.

## Driver compatibility detail

`pg` 8.23.1 and `pg-cursor` 2.22.1 are pinned. PostgreSQL transaction state is read through one isolated `client.connection` ReadyForQuery event hook because the public high-level API does not expose it. Docker tests cover idle, open, failed, rollback-to-savepoint, and committed states. Revalidate this hook before upgrading the driver.

MySQL transaction status comes from EOF/OK packets through one isolated `mysql2` command hook. MariaDB exposes the corresponding status as `connection.info.status`; its runtime pause method supports metadata backpressure. After errors, COM_PING recovers authoritative status (error packets carry no status flags). PING resets ROW_COUNT(), so successful queries use their own status flags and retain diagnostics without a probe. Docker tests validate these contracts, including status after statement errors, DDL commits, and manual mode. Revalidate these version-pinned integration points when upgrading. Context refresh queries run after USE or statements referencing SQL_MODE; those commands can therefore change diagnostics before the next execution.

MySQL/MariaDB result caps do not inject LIMIT or kill the user's query. They drain the wire response with backpressure and discard excess rows. Cancellation is still available while draining. Disconnects during nontransactional work or commits may have an unknown outcome. Schema discovery uses another connection and does not list console-local temporary tables.

SQL Server uses the public `execSqlBatch` and request pause/resume/cancel APIs, plus one internal `tedious/lib/value-parser.readValue` hook isolated in `sqlserver-values.ts`. It is enabled only for Db Commander connections and must be revalidated before any Tedious update. The default driver converts decimal to Number and temporal values to Date, which would lose precision/offsets. The hook decodes these TDS types as strings before conversion; other types retain upstream handling. Server-specific spatial/hierarchy types do not yet have specialized viewers.

A status query runs after each complete **execution** (not between its GO batches), including after acknowledged errors/cancellation. It changes `@@ROWCOUNT`, `@@ERROR` and similar diagnostics before the next execution. Inspect such values inside the same submitted execution. This probe preserves physical session ownership and observes implicit transactions and any server rollback at batch completion. Metadata uses a separate connection and cannot see local temporary tables. Connection loss or consumer/protocol failure discards the session and reports an unknown outcome; there is no automatic replay.

`oracle-values.ts` overrides only the selected connection’s read-buffer date decoder, never an upstream prototype. It requires node-oracledb 26.0.0 and fails explicitly if the expected internal shape changes. Docker tests cover native and implicit results, fixed/named time zones, LTZ, early dates and isolation from ordinary unmodified connections; unit cases cover calendar rollover and malformed encodings. Revalidate this hook on any driver update. DBMS_OUTPUT preview is limited to 1 MB per execution and 1,000 lines per statement; internal GET_LINES calls mean PL/SQL diagnostics should be inspected inside the submitted block.

The utility process provides crash containment, not a permission sandbox for third-party native code. No plugin loader is currently exposed.

## Editable-grid milestone

- A typed, strict `editGrid` IPC/RPC contract reaches the production registry and every driver. Table selection is explicit; no editable lineage is inferred from arbitrary SQL. Base-table metadata supplies all columns, primary/composite keys, default/generated flags and a schema fingerprint. Names are quoted; catalog filters and all row values use actual driver bindings. The MySQL text-protocol exception is limited to fixed, parameter-free transaction controls.
- One editor and original snapshot belong to each physical connection, including the SQLite worker. Originals are never accepted from the renderer. The registry serializes table operations against queries, metadata and disconnect; concurrent tabs remain independent. Accepted console executions invalidate older table snapshots. A mutation consumes its snapshot before sending DML, preventing replay of a timed-out/repeated request.
- Apply requires idle transaction state and normal autocommit configuration (Oracle's native manual mode is supported). It starts a transaction, locks the table/metadata where supported, checks schema drift, locks each target row by its complete key, and compares every fetched value exactly in JavaScript before writing. SQL Server uses UPDLOCK/HOLDLOCK; PostgreSQL/MySQL/MariaDB/Oracle use row locks; SQLite uses BEGIN IMMEDIATE; DuckDB relies on MVCC/write-conflict detection. Every operation must affect exactly one row. Failure rolls the entire owned batch back; success leaves it open for explicit Commit/Rollback in that tab. Existing user transactions are never implicitly committed or rolled back by the grid.
- Prepared values preserve literal quotes, backslashes, Unicode, NULL and exact integer/decimal text. MySQL/MariaDB conversion warnings fail the batch. Generated values and existing keys cannot be overwritten. DuckDB generated expressions are identified from its canonical CREATE text because the public column-default field includes ordinary defaults too. ## Optional password-storage milestone

The main process uses pinned `@napi-rs/keyring` 2.1.1 asynchronous native entries: macOS Keychain, Windows Credential Manager, and explicitly selected persistent Linux Secret Service. No file-based secret store, encryption-key file, `safeStorage` basic-text backend or transient kernel-keyring fallback is used. The native binding loads only when credential operations are requested; inability to load or access it produces a session-only option and a sanitized error.

Saved passwords are opt-in per profile. Connect remembers a submitted password after authentication succeeds; Save profile can store it offline. Editing permits replacement or immediate removal. Profile deletion removes the entry first and retains the profile on failure. Live sessions keep their current in-memory credentials. Blank passwords can be used for a session but are not persisted; access tokens and embedded-file profiles are excluded. Backend size limits still apply to long passwords.

An OS entry contains the password, profile UUID and SHA-256 fingerprint of engine/host/port/database/user/authentication/TLS/CA settings. The service namespace includes a hash of the local user-data path. The broker checks both the current persisted profile and stored fingerprint before opening a connection. A display-name change retains the secret; any connection/trust change removes it. Neither `connectSavedPassword` nor any other preload method returns a stored password. Session cloning now happens in main, so the renderer also does not need an in-memory saved password to open another physical session. Disconnect, session loss and host loss clear main's session cache; SQL-driven and sidebar database changes update only its connection context.

Workspace version 2 gains an optional, non-secret `credential: "os-store"` marker on a saved profile. Main owns markers: ordinary renderer workspace saves cannot forge, drop or restore them. Credential changes and workspace writes serialize. Before a native write, the marker is persisted so interruption cannot orphan an untracked new entry. Failed writes may leave a marker referencing a missing entry; the UI reports the error and supports retry/removal. Missing or malformed entries never connect with a guessed or empty password. Quit waits for pending credential operations before the normal workspace flush. SQL buffers, results and sessions are never replayed on recovery.

The native lifecycle desktop tests use isolated workspace namespaces and remove only their own test entries. They verify opt-in versus session-only behavior, empty password inputs after restart, real backend contents, rename/replace/remove/delete, changed-setting guards, plaintext absence in workspace/WAL files and history, unavailable providers, failed writes/deletes and externally missing entries. Failures are injected into the native binding only from Playwright's main-process debugger; production has no mock-vault environment switch. The PostgreSQL Docker workflow authenticates using a saved entry after restart, creates independent sessions without sending the secret back to the renderer, and checks that removal preserves live sessions and renderer recovery stays disconnected. Oracle schema-only mode uses the Data Pump row filter; imports suppress source-user recreation and allocate new object IDs.

Restore refuses a backup file still open by this host so inspecting its header cannot disturb POSIX file locks.

Azure SQL has a distinct, explicitly confirmed, billed same-logical-server recovery-copy workflow. It monitors the copy until ONLINE and restores by copying that recovery database into another new name. It is not BACPAC or point-in-time recovery. Cancelling monitoring never silently drops an Azure database and reports an unknown outcome.

Jobs are bounded (two active, forty retained), keep credentials out of their records, redact native diagnostics and hold the originating tab's operation lock. Renderer actions and host checks prevent conflicting SQL, edits, database switches and disconnects; Oracle's idle manual commit mode is allowed. Quit has a separate unfinished-job decision. An atomic metadata journal recovers interrupted jobs as unknown after restart; renderer/host crashes do not replay work. Restore never automatically replaces or drops an existing target. Partial server results, native remapping limitations and required privileges are described in [the usage guide](BACKUP_RESTORE.md).

## Data import and full-result export

The results toolbar separates **Export preview** (cached CSV, no SQL execution) from **Export all rows** (explicit reviewed re-execution). A result-owned review snapshots its SQL, native result index and tab/session context instead of reading the current editor. Native result indexes remain unchanged for preview-cache lookup. Parameter values are not retained or reused. The shared single-read-query validator runs in the renderer and again in the transfer host; ambiguous source, whole scripts and writes require explicit isolation before execution. DuckDB attaches scanner source text only when its unit count agrees with native extraction, otherwise source text stays unavailable. SQL Server result sources remain native batches; multi-statement batches are never silently split or replayed for export.

Result selection is automatic only until the user chooses a result or output pane in that execution. Incoming metadata/rows and terminal states prefer the first fetched row set, then an empty tabular set, then a statement outcome. Selection preserves native source/result indexes and partial results on failure/cancellation. Result descriptions and footers distinguish fetched preview rows/limits from affected-row outcomes.

**Import / export** opens a native modal with file selection, source/target review and session-specific progress/cancellation. The active editor selection supplies export SQL; otherwise the entire editor buffer is copied for review. Imports select an existing table, preview ten records, map headers to target columns or skip them, and explicitly start a transaction. Jobs own the same session lock used by browsing, editing and database switching; other sessions remain independent. Active jobs participate in quit protection. Terminal events update the owning tab's transaction state and expire editable snapshots. Jobs, previews and imported values stay in memory; a host failure marks active jobs unknown and never replays SQL.

The UTF-8 CSV/TSV reader handles BOMs, CRLF/LF, escaped quotes and embedded newlines across file chunks. Headers must be nonempty and unique. Unquoted `\N` is NULL; quoted `"\N"` is literal text; empty fields are empty text. Source identity (file metadata) and table definition are checked against the reviewed preview and again around execution. Mappings use current catalog columns, quoted identifiers and bound values. Generated columns cannot be assigned, omitted columns use defaults, and required columns must be mapped. Integer/numeric/boolean syntax and known length/scale limits are checked before each write; native constraints and MySQL/MariaDB conversion warnings also fail the batch. PostgreSQL destination types are inferred, avoiding silent `VARCHAR(n)` cast truncation.

Imports support the table editor's built-in scalar type whitelist, up to 100 columns, 16,384 characters per cell and 1 MiB per record. Primary keys are not required for append-only imports. Unsupported complex/LOB columns, views, virtual tables, read-only files and nontransactional MySQL tables remain ineligible; MySQL/MariaDB tables with triggers or temporary-table shadows are refused. Database triggers/defaults retain their native effects, including any external or autonomous effects that ordinary rollback cannot undo. Oracle treats empty text as NULL and uses the existing connection's temporal formats. SQLite preserves signed 64-bit integers, rejects integer overflow and retains native affinity semantics for other numeric columns; use text columns for exact decimal text. This is a sequential parameterized importer, not a native bulk loader.

A failed or cancelled import reports the record and attempts full rollback. If rollback/state cannot be confirmed, it reports an unknown outcome. Cancellation is cooperative between records and waits for the current database call (including its driver timeout/lock wait). Success leaves all imported rows uncommitted in that physical tab session. A source file modified in place during reading fails the import; file identity checks are not a cryptographic guarantee against malicious concurrent rewriting.

Exports support CSV, TSV and JSON for a single SELECT/CTE result. Obvious script/write forms are refused, but SQL functions can still have side effects; the dialog explicitly confirms execution. No background replay of a previous query occurs. Full exports use native streaming/cursor execution, bounded batches and file backpressure, bypassing the 1,000-row/8 MiB preview retention limits. They retain the previous fetched-row cache and do not send exported rows through renderer IPC. An individual decoded row exceeding 8 MiB fails instead of silently truncating it. Native driver buffers, one large server value and database execution may still require substantial memory/work; no ten-million-row memory benchmark is claimed.

CSV/TSV quotes every non-NULL field, preserving empty strings and literal NULL markers. It deliberately preserves formula-like strings; spreadsheet formula neutralization is not applied. JSON uses `{ "columns": [...], "rows": [[...]] }`, preserving duplicate column names through positional rows and exact scalar representations as strings or null. Export is a data transfer, not a backup or universal cross-engine type conversion. Importing binary/complex values requires explicit SQL conversion and supported target columns. [Db Commander JSON import](#streaming-json-data-import) accepts this envelope with unique column names; [SQL INSERT export](#sql-insert-export) is implemented with runtime validation deferred. Other JSON layouts, spreadsheet formats and continue-on-error reject files remain later work.

Files are written to a private temporary directory beside the destination, closed and synced, then linked without overwriting. Cancellation/failure removes the temporary file and leaves the destination absent. A process crash can leave a private temporary directory; no partial file is advertised as successful. Job state is transient rather than a resumable transfer journal. Existing fetched-preview CSV export remains available separately.

### Reviewed object source and routine calls

The inspector previews available create, alter and drop scripts for views, routines, triggers and DuckDB macros. The source editor retains the loaded definition and draft independently, checks the current definition at review, and revalidates the retained plan and source before execution under the existing session and operation safeguards. The reviewed declaration must identify the selected object and, for triggers, its parent. Authored source is reviewed as SQL and is not presented as a generated migration.

Local contract fixtures cover PostgreSQL 17, MySQL 8.4, MariaDB 11.4, SQL Server 2022, Oracle Free 23.26.3 and the embedded SQLite and DuckDB engines. The Azure SQL profile is exercised against the local SQL Server fixture, not a live Azure service. These contracts use isolated local credentials and do not qualify every authentication mode, server version or desktop OS. Platform and package qualification is reported separately for the exact build; no new authentication path is introduced by this editor.

Each review is retained in memory for ten minutes, with at most one per session and twenty overall. Strict IPC schemas accept structured changes, including authored default expressions, generated expressions and index predicates. These SQL fragments are bounded to one line and reject comments, statement separators and unbalanced delimiters; defaults and generated expressions are enclosed in parentheses. MySQL/MariaDB are checked under both string-escape and identifier-quote modes; PostgreSQL ordinary strings with backslashes require explicit E strings. These structural checks do not validate function behavior or eliminate side effects: the exact expression and a warning appear in the review, and the database validates its semantics. Identifier lengths are checked before quoting; literal defaults are escaped, with MySQL/MariaDB text encoded independently of `NO_BACKSLASH_ESCAPES`. Existing targets resolve through the visible catalog and a metadata fingerprint before review and again before execution. Truncated metadata is refused. This catches stale reviews; it does not lock out concurrent DDL between inspection and execution. Native permissions and dependency checks remain authoritative. A consumed plan cannot be retried, even after failure or cancellation.

Existing-column edits use the fingerprinted catalog definition. PostgreSQL and SQL Server retain the old collation when the replacement type supports it; SQL Server reconstructs type modifiers from complete metadata and refuses sparse, masked, encrypted, hidden and other unsupported attributes. SQL Server default changes review removal and recreation of the named constraint in the owned transaction. MySQL/MariaDB type and nullability changes retain the complete native column definition; inconsistent or escape-mode-dependent metadata is refused, and changing a type explicitly replaces type-specific attributes. MySQL requires a second implicitly committed statement to restore the absence of a default on a nullable column, with an explicit partial-failure warning. MariaDB represents the absent default as DEFAULT NULL when the column becomes nullable, which is also shown in the review warning. SQLite NOT NULL changes require version 3.53 or later and a complete definition with no implicit or redundant NOT NULL clause; no table rebuild or writable-schema edit is performed. Oracle `DEFAULT ON NULL` is retained when changing its value; removing it requires separately reviewed SQL. Older servers may omit optional metadata without breaking catalog browsing; edits that need it fail closed. The database remains authoritative for conversions, locks and dependencies.

Foreign-key references resolve through the visible catalog, and each referenced table is fingerprinted at review and rechecked before execution alongside the changed table. Composite columns are selected in matching order. SQLite references stay within the same attached database and rely on the connection’s foreign-key setting; DuckDB references are limited to the active catalog. MySQL and MariaDB versions that can ignore checks are rejected. SQL Server uses NO ACTION rather than RESTRICT, Oracle exposes supported delete rules only, and DuckDB is limited to NO ACTION. Server-specific permissions, data checks and enforcement settings remain authoritative. Replacement uses one ALTER TABLE for MySQL/MariaDB and two reviewed statements elsewhere. On Oracle, both statements commit implicitly: a failed add can leave the old constraint removed, which is warned and requires destructive acknowledgment. No automatic CASCADE or table rebuild is added.

Native built-in type names come from an engine-specific allowlist. Length, numeric precision/scale and temporal fractional precision are validated as separate numbers, never interpolated as arbitrary SQL. PostgreSQL 15+ and Oracle support negative scale and scale above precision within engine limits; older PostgreSQL, MySQL/MariaDB, SQL Server and DuckDB use their more restrictive rules. Named types use separately quoted catalog/schema/name components (catalog is available for DuckDB), not raw type SQL. Their definitions are not locked or fingerprinted by the change plan, so the review warns to inspect those dependencies and permissions separately. The server remains authoritative for extension availability and type-specific rules.

Identity definitions use PostgreSQL/Oracle `GENERATED ... AS IDENTITY`, SQL Server `IDENTITY`, MySQL/MariaDB `AUTO_INCREMENT`, or SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`. MySQL/MariaDB require the identity as the first primary-key column or an explicitly selected unique key; the latter also permits adding an identity to an existing table. SQLite cannot add an identity without a table migration, and DuckDB has no identity syntax. Adding identity values to existing rows is warned as unordered. Generated columns use a single bounded, structurally checked SQL expression and expose virtual/stored choices according to the engine: PostgreSQL virtual requires version 18, SQLite cannot add stored generated columns, DuckDB cannot add generated columns after creation, and Oracle supports virtual columns. SQL Server infers the computed type and uses `PERSISTED` for stored columns. Default and generation definitions cannot coexist. Generated primary-key support follows the engine/storage combination; the server remains authoritative for determinism, dependencies and permissions. The grid continues to reject direct edits of generated values.

PostgreSQL, SQL Server/Azure SQL, SQLite and DuckDB normally run the reviewed statements in a new transaction on the tab’s existing physical session. Successful changes remain uncommitted for the toolbar’s Commit/Rollback controls. PostgreSQL concurrent index builds are the exception: they require idle autocommit and explicit acknowledgment, and cannot be rolled back. The editor requires an idle session and does not join, commit or roll back unrelated work. Failed/cancelled changes roll back the owned transaction when the connection and rollback are confirmed. Unexpected transaction termination, failed rollback or connection loss reports an unknown outcome instead of claiming that nothing changed. MySQL, MariaDB and Oracle execute DDL with implicit commits and no rollback promise; active transactions are rejected, as is disabled autocommit on MySQL/MariaDB. Oracle’s idle manual-commit mode is allowed.

The existing per-session operation lock prevents concurrent queries, edits, backup/import/export, switches and disconnects while preparing/applying. The UI additionally blocks unresolved grid drafts. The native quit guard tracks in-flight schema execution. Cancel uses the native driver cancellation path; each statement requests cancellation after 60 seconds and waits for settlement. Metadata cancellation waits for its bounded read before stopping. A write RPC has no renderer timeout that could release ownership prematurely. Host/renderer recovery never restores plans or replays DDL.

Host-only execution preserves the original SQL buffer and fetched-result cache, invalidates grid snapshots, and records submitted SQL (including transaction control and automatic rollback) in query history. The dialog reports the final state. Catalog refresh runs when the session is idle and after Commit/Rollback for transactional DDL, avoiding separate catalog reads that could block on the tab’s own schema locks. Saved review SQL includes BEGIN where appropriate and deliberately omits COMMIT; execution of a saved script outside the guided editor follows ordinary SQL-console behavior.

Existing-column alterations, constraint design, identity/generated columns and expression defaults were added after the original milestone, within the limits described above. View/routine editing forms, automatic SQLite rebuilds, cross-user Oracle changes and dependency migrations remain outside this editor. Existing schema/catalog visibility limits still apply. Temporary-object DDL uses the SQL console. SQLite type affinity and each engine’s precision/collation rules remain native semantics, not a promise of identical storage across engines.

### SSH transport

The database utility host owns an `ssh2` client and an ephemeral IPv4-loopback listener for each tunneled session. The fingerprint is mandatory, SHA256/base64 in OpenSSH format, and must come from a trusted source. Missing/mismatched keys fail closed; there is no accept-any or automatic trust-on-first-use mode. Authentication uses a password, an encrypted or unencrypted private-key file (absolute path, regular file, at most 256 KiB), or `SSH_AUTH_SOCK` / the Windows OpenSSH-agent named pipe. No shell commands, agent forwarding or user SSH-config execution is involved. Jump chains, MFA/keyboard-interactive, OpenSSH certificates and known_hosts import are not implemented.

Database Host remains the TLS identity. An optional **Database host from SSH server** overrides only the SSH forwarding destination (useful for a bastion-side alias); the database port is the remote port. Every primary, metadata and cancellation socket uses the managed route. PostgreSQL retains the original TLS server name/check; MySQL/MariaDB use socket factories and retain their hostname checks. SQL Server uses the pinned Tedious connector contract and rejects changed redirect targets. Oracle uses its supported HTTP CONNECT proxy with a fixed destination and verified TCPS, preserving native listener/server identity checks. Azure SQL requires a fixed/Proxy endpoint; redirected Oracle endpoints are rejected. SQLite and DuckDB reject SSH configuration.

Disconnect and failed connection attempts close listeners, channels and SSH clients. Database switching opens a candidate tunnel before retiring the old session; a failed switch keeps the original connection. Tabs have independent SSH clients. SSH keepalives and existing driver deadlines bound liveness; a lost tunnel closes forwarded sockets and reports disconnected/unknown work. There is no automatic reconnect or SQL replay. The process exit closes all owned sockets. Forwarding is confined to the configured database destination and capped per tunnel.

SSH passwords and private-key passphrases remain only in live connection memory, including explicit tab cloning. The saved profile contains the key path, never its contents; workspace validation rejects SSH-secret fields. Database passwords can still use the OS vault. A saved password's binding now includes SSH endpoint/user/authentication/trust/destination settings; changes require explicit password entry and remove obsolete vault entries. Folder/favorite/environment edits retain the password binding. Existing direct-connection vault bindings are unchanged.

PostgreSQL native backup/restore retains `PGHOST` for verification and uses `PGHOSTADDR` plus the forwarded port for transport. SQL Server and Oracle server-side backup operations use the routed adapters. Native MySQL/MariaDB backup/restore is explicitly unavailable over managed tunnels until their CLI hostname/transport separation is implemented; use a direct connection for those operations. Query, schema, grid, import and export paths are supported through the tunnel.

### Protected profiles

Production labels always enable protection; any other profile can opt in. Every protected connection starts locked. Unlock requires typing the exact connection name and lasts ten minutes for that physical session. A new tab, reconnect, database replacement or app recovery starts locked; unlock timestamps never enter workspace storage. The dialog identifies the connection/database/host, and the active target banner always shows its environment and lock state. Manual relocking is immediate for future operations.

The host rejects console SQL while locked, including SELECT: keyword classification cannot reliably identify side effects across all SQL dialects. It also guards grid apply, reviewed schema apply, imports, full-query exports, restores and Azure recovery-copy creation. Catalog inspection, table browsing, review preparation, cached-result exports, ordinary backups and cancellation remain available. Exact standalone COMMIT/ROLLBACK statements remain allowed to settle existing transactions. Unlock expiry does not interrupt an operation already started or silently settle a transaction. These are accident-prevention controls, not a database authorization boundary: use restricted database accounts for enforced read-only access. Browsing views and server-side functions still follows native database permissions.

## Query plans

**Explain** takes the editor selection, or the whole buffer when nothing is selected, and opens a review/viewer. It does not submit SQL until **Get estimated plan** or **Execute and analyze** is pressed. The request schema carries SQL, mode and an explicit execution acknowledgment; dialect commands and connection routing are generated by the database host. Protected profiles must be unlocked in either mode. Scripts, existing EXPLAIN commands, executable MySQL comments and ambiguous backslash-quoted literals are refused. This is a deliberately conservative statement-boundary check, not a general SQL validator. Native parsers and permissions remain authoritative.

| Engine | Estimated plan | Session behavior |
| --- | --- | --- |
| PostgreSQL | `EXPLAIN (FORMAT JSON, VERBOSE, COSTS, SUMMARY)` | Uses the tab's session, temporary objects, settings and transaction. |
| MySQL / MariaDB | `EXPLAIN FORMAT=JSON` | Uses the tab's session. Each engine retains its own JSON structure; no cross-engine cost equivalence is implied. |
| SQL Server / Azure SQL | `SET SHOWPLAN_XML ON`, then a SELECT/WITH query in a separate batch | Disposable connection to the current database. SHOWPLAN cannot leak into subsequent tab queries. Requires SHOWPLAN permission for referenced databases. DML and control/batch statements are not accepted in this viewer. |
| Oracle | `EXPLAIN PLAN SET STATEMENT_ID ... FOR ...`, then `DBMS_XPLAN.DISPLAY` | Disposable connection, unique statement ID, rollback of plan-table writes and close in finally. Needs PLAN_TABLE and DBMS_XPLAN access. No user transaction is committed or rolled back. |
| SQLite | `EXPLAIN QUERY PLAN` | Uses the tab's session, including attached/temp databases. Raw native rows are retained; output is version dependent. |
| DuckDB | `EXPLAIN` | Uses the tab's session; respects its current EXPLAIN output settings and returns native text. |

SQL Server and Oracle planning connections use profile defaults and cannot observe tab-local settings, temporary objects or uncommitted schema changes. Their plans can differ from plans compiled in the query tab. Managed SSH routing and original database TLS verification are retained for those additional sockets. No adapter falls back to executing a query when planning fails. Estimated planning is not a database security boundary: optimizers may evaluate functions, consult external resources or invoke user-defined costing code.

Only PostgreSQL exposes execution statistics in this milestone. Its Analyze option adds `ANALYZE, BUFFERS, TIMING` to the JSON request and requires a fresh acknowledgment for each execution. The selected statement really runs: DML, writable CTEs and function side effects follow the existing transaction mode. Autocommit can commit writes immediately. Open transactions remain open, and PostgreSQL errors/cancellation can leave them failed until Rollback. There is no implicit BEGIN/COMMIT/ROLLBACK wrapper and no promise to undo external or sequence side effects.

The PostgreSQL viewer presents an expandable tree, cost bars relative to the root, estimated rows and inclusive total cost, actual per-loop rows/timing, loops, summary planning/execution time and an operator-detail table including native predicates/buffers. Child costs and times are not summed or mislabeled as exclusive. Raw JSON is always available; unrecognized node shapes fall back to raw output. JSON and XML are displayed as inert text, never HTML or executable content. The tree stops at 1,000 nodes/100 levels, with a notice; raw output remains complete within the capture limit.

Captures are limited to one million encoded row bytes and 2,000 rows; oversized output fails visibly rather than presenting a truncated plan as complete. Native drivers can allocate an individual row before this bound is enforced. A per-session operation lock prevents concurrent writes, schema work, transfers, switches and disconnects. Cancel follows the native driver path, or cancels/breaks the disposable planning connection. A 60-second deadline requests cancellation and awaits settlement. SQLite cancellation retains its existing worker/session termination semantics. Connection loss can report an unknown outcome; no plan or SQL is automatically replayed.

The original buffer and fetched-result cache remain intact. Captured plans are dated, labeled estimated/actual and retained in memory per tab; new sessions and application restart discard them. Submitted plan commands are recorded in existing local query history, but plan output is not persisted unless explicitly copied/saved. Save uses a native file dialog with JSON, XML, text or TSV extension. XML/other-engine graphical renderers, plan comparison/import, plan image export, actual plans outside PostgreSQL and SQL Server DML/batch planning are follow-up work.

References: [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html), [MySQL EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html), [MariaDB EXPLAIN](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/analyze-and-explain-statements/explain), [SQL Server SHOWPLAN_XML](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql), [Oracle EXPLAIN PLAN](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/EXPLAIN-PLAN.html), [SQLite query plans](https://www.sqlite.org/eqp.html), and [DuckDB EXPLAIN](https://duckdb.org/docs/current/guides/meta/explain).

## Value inspection, column controls and foreign-key navigation

Double-click or Enter on a captured result cell opens a read-only inspector; editable grids have an explicit Inspect action that also displays staged values. Opening it never submits SQL. XML is validated and shown as an inert structure outline plus original text: DTD/entity declarations are rejected and markup is never inserted into the document as HTML. Hex displays native binary bytes when their encoding is known, otherwise it explicitly shows UTF-8 bytes of the text representation. Offset/ASCII views page in 4 KiB increments.

Inspection displays at most 262,144 UTF-16 code units of text (without splitting a surrogate pair), or 131,072 binary bytes. Copy/save uses the displayed representation, including only the current hex page. Native save dialogs select JSON/XML/text and new files use mode 0600. A current value can differ from the original page; this is labeled and never replaces the optimistic-concurrency originals. No usable primary key means only the existing snapshot is available; unsupported placeholders require explicit SQL. Changed/deleted objects, missing permissions and native conversion errors are surfaced. MySQL/MariaDB temporary tables that shadow persistent key metadata are refused.

| --- | --- |
| PostgreSQL | Native text casts for scalar/JSON/XML values; bytea via hex encoding. |

## Query library and bound parameters

**Query library** exposes paginated history (25 entries per page) with literal SQL substring search, exact connection/database filters, engine, status, UTC date range and favorites. Execution context comes from the host's session registry; history stores the original submitted SQL, time, duration, status and optional parameter names/types. A script's context is captured at its start. Preflight failures that submit no SQL do not create history. The recent sidebar keeps its latest-100 view and now opens SQL in a new independent tab. Opening any library item preserves the current buffer and never executes the opened SQL; review its target connection before running.

Workspace storage migrates to SQLite schema version 3 while keeping the version-2 workspace JSON contract. Version-2 databases receive a consistent `workspace.sqlite.v2-backup-*` snapshot before alteration; version-1 recovery retains its existing backup/migration path. Existing history is preserved with an unknown engine and empty database/parameter metadata. Migration is idempotent and newer schemas are refused.

Global retention defaults to recording enabled, 500 executions, no age expiry and favorites exempt from automatic age/count pruning. Limits allow 1–10,000 executions and 0–3,650 days (0 disables age expiry); applying limits prunes immediately. Cleanup also runs at startup, read and write. Favorites are separately limited to 500 entries / 32 MiB of SQL; total history SQL is capped at 64 MiB. Disabling recording retains existing entries. Recording must be enabled both when work starts and when it completes; enabling it during a running private query does not capture that query. Saved profiles have an optional recording toggle, applied at connect/reconnect. Individual deletion and explicit clear can include or preserve favorites. SQLite secure deletion and a clear-time WAL checkpoint do not remove SQL from buffers, old migration backups or external filesystem backups.

Snippets have a name, description, optional engine label, SQL and favorite flag. Search covers name, description and SQL; favorites sort first. Up to 200 snippets, 100,000 SQL characters per snippet and five million SQL characters total are supported. Snippets survive history clearing and restart. They are local, unencrypted templates, without saved parameter values. Engine labels are descriptive: opening uses the active connection, and users must check dialect and target. Snippet synchronization, import/export and categories are follow-up work.

Parameters use case-sensitive ASCII `:name` markers (1–64 characters, starting with a letter/underscore). Quoted strings/identifiers, comments, PostgreSQL casts/dollar strings and Oracle alternative quotes are excluded. MySQL/MariaDB mode metadata follows the session's NO_BACKSLASH_ESCAPES and ANSI_QUOTES settings into the prompt and host compiler. Monaco quote auto-insertion is disabled under NO_BACKSLASH_ESCAPES to avoid adding quotes using incompatible escape rules. The shared compiler validates unique/matching names and a single SELECT/WITH/INSERT/UPDATE/DELETE statement, then rewrites only marker spans. It refuses scripts, executable MySQL comments, session commands and mixed native placeholders. The native engine remains the final SQL parser.

Text, signed 64-bit Integer, Boolean, NULL and Hex parameters bind via PostgreSQL cursors, MySQL prepared execution, MariaDB prepared streams, Tedious RPC parameters, Oracle bind objects, SQLite statement bindings and DuckDB prepared bindings. Integer conversion never passes through a JavaScript floating-point number; casts make string-backed integer/boolean transport explicit. NULL uses native context inference. Native empty-string, type/collation, binary formatting and transaction semantics remain engine-specific. Decimal, Date and Timestamp were added in the later [typed-parameter milestone](#decimal-date-and-timestamp-parameters). The prompt supports 100 distinct names, 1,000 occurrences, 65,536 characters per value and 262,144 total value characters; hex accepts byte pairs without a prefix. Arrays, identifiers, OUT/PLSQL parameters and parameterized scripts are not supported.

The prompt captures the selected SQL and target session. Cancel preserves existing results; a run uses the ordinary operation lock, protected-profile guard, bounded result streaming, cancellation and transaction handling. Values remain in memory for execution only. History stores only parameter names/types and SQL; snippets/workspace store SQL templates. Results and transient server errors can display supplied values, as can server logs under server policy. Fetched-result CSV uses captured results without asking for parameters again. The full-result export dialog now prompts for bound parameters (see its milestone below). EXPLAIN also prompts for typed bindings (see its milestone below); it never substitutes literals. Formatting supports portable markers across all dialects and verifies their identities after formatting.

## Keyed and bounded data comparison

The validated `compareData` RPC reserves both registry operation slots synchronously. It requires identical connection engine/profile types, a selected database and idle transactions; non-Oracle manual commit modes are rejected. Both table identities are checked against complete visible base-table catalogs before and after collection. The host-only `compare-data` grid operation reuses each adapter’s bound native transport and metadata without invoking user SQL, result streaming, history or mutation authorization. It never invalidates the retained editor snapshot or originals. Protected profiles remain locked, and embedded read-only connections can compare.

Capture defaults to declared primary-key columns or accepts an explicit key of at most eight columns. Explicit keys need only be unique and non-null within the selected complete scope; this does not certify global uniqueness. Selected names and adapter-reported native types must match; target column order is aligned by name. Matching uses encoded key tuples (not delimiter concatenation), exact captured values and separate NULLs. SQLite storage-class prefixes are retained. Session-dependent numeric/date formatting, whitespace, JSON text and collation are not normalized; these can produce differences. Permission-based row filtering is not bypassed.

Each side uses one bounded SELECT for row values, reading limit + 1 rows. Limits are 1–200 rows per side (default 100), 32 selected columns including keys, 4,096 characters per value and 4 MiB of UTF-8 JSON row data per side. Exceeding a limit aborts the report, so unrelated page prefixes never become false missing-row results. The table metadata adapter retains its 100-column ceiling; the catalog retains its existing visibility/2,000-object ceiling. Unsupported selected types, NULL/duplicate keys, conversion warnings and schema drift fail explicitly. MySQL temporary-table shadowing is refused; SQL Server’s TEXTSIZE must be large enough to prevent silent truncation. Filters reuse catalog-validated identifiers, fixed operators and bound values from the table browser.

Both sets are sequential live reads, not an atomic cross-database snapshot; concurrent DML can produce transient differences, and changes after capture require refresh. Row/byte limits do not bound server scan work. A 45-second budget is checked between collection phases, while native statements follow their adapter behavior and may outlast it. The main RPC remains owned until the host finishes; it does not release the UI’s operation guards on a renderer timeout. This milestone has no separate comparison cancellation or synchronization/DML path.

The dialog opens from table/database context menus or Commands, offers source/target tables, implicit or explicit keys, column selection, separate AND filters and a row limit. Scope edits discard earlier results. Results include counts, source-only/target-only/changed/matching rows, exact side-by-side cells, display search/status filters and 25-row display pages. JSON reports include scope/filter values and captured rows, use the existing native save dialog/file permissions, and are capped at 1 MB. Captured rows remain only in dialog memory unless explicitly saved; they are not placed in recovery storage, query history or the clipboard.

## Migration-file export

Both guided schema-change reviews and selected same-engine schema-comparison suggestions support forward migration-file export. `MigrationExports` retains canonical generated statements in the utility process, using opaque source and preview IDs. Strict IPC accepts a bounded selection, an ASCII description (1–80 characters), transaction mode and destructive opt-in; it accepts no SQL or destination path. Guided export uses the generator’s statement array, not a parser that strips BEGIN from the displayed review. Comparison export excludes native reference definitions and rejects selected objects without included executable suggestions. Matching/unknown objects cannot become migration statements. Supported statements retain their deterministic source order; there is no dependency sorting or namespace rewriting.

The export preview contains exact UTF-8 file contents, engine/target/capture context, warnings, a SHA-256 checksum and a UTC timestamp plus normalized name. Headers and metadata are commented separately on every CR/LF/Unicode line. No credentials or session IDs are added. SQL/defaults, database/object names, connection labels and comparison endpoint/file context remain visible in files. The preview is read-only; changing its name or transaction option invalidates the preview and acknowledgments. Destructive statements require an additional acknowledgment enforced again by the host.

Default output contains no transaction commands so an external runner can own its transaction. Optional wrapping uses BEGIN for PostgreSQL/DuckDB, BEGIN IMMEDIATE for SQLite and BEGIN TRANSACTION for SQL Server/Azure SQL, followed by COMMIT. MySQL/MariaDB/Oracle reject wrappers because DDL commits implicitly. Files warn that a runner must stop on the first error and roll back failures explicitly; no engine-specific exception handler, idempotency, automatic rollback or retry is generated. A comparison file remains a partial suggestion set, even when every selected object supplies some SQL.

The native save dialog suggests a timestamped `.sql` filename. The main process revalidates the retained preview after the chooser returns, then exclusively creates a new file (`wx`, mode 0600 where supported), writes UTF-8 and flushes it. Existing paths, including symlinks, are refused; cancellation creates nothing and a write failure cleans up its partial file. Saving does not run database commands, unlock production profiles, record history, alter transaction state or replace editor/grid results. It can also archive an already-applied review while its snapshot remains available; it does not imply that the target still needs the change. Live schema drift is not rechecked during export, and scripts carry that warning.

Retention is in memory only: at most 20 source snapshots (8 MB each, 16 MB combined) and 20 previews (1,000,000 UTF-8 bytes per file). Reviews expire after ten minutes; previews cannot outlive their source. Disconnect/database replacement/host shutdown invalidates participating sources and previews. Sources outside retention bounds are unavailable for export. File paths are chosen in the native main-process dialog, never supplied by the renderer. No workspace migration or dependency changes were needed.

Every refresh matches the original transaction. A new transaction on the same native session is never silently substituted. Snapshots distinguish observation, reported rollback, no longer visible, unavailable and unsupported. Visibility is permission-dependent and non-atomic; “no longer visible” is not proof of completion. Oracle parallel recovery reaching 100% describes that record only, not all cleanup/lock release. A cancellation may leave the overall transaction active and locks held, and an already disappeared target cannot be reconstructed without an earlier capture. Failover/restart and distributed/cluster recovery are outside this bounded connection-scope inspection; no cross-server identity guarantee is claimed.

Monitoring privileges are separate from action privileges. PostgreSQL needs same-user visibility or sufficient statistics privileges; MySQL needs `PROCESS` and access to `performance_schema.threads`; MariaDB needs `PROCESS`. SQL Server uses the applicable `VIEW SERVER STATE`/`VIEW SERVER PERFORMANCE STATE` grants; Azure visibility additionally depends on service/database scope. Oracle needs `SELECT` on `SYS.V_$SESSION` and `SYS.V_$TRANSACTION`; `SYS.V_$FAST_START_TRANSACTIONS` is optional. Missing optional Oracle recovery access leaves ordinary undo observations usable and is labeled explicitly. The application never grants permissions. Disposable tests grant/revoke them inside the existing fixture containers.

UI data is transient and excludes SQL text. The panel labels capture/read/expiry times, native identity, counters, progress and interpretation limits; it supports manual refresh and dismissal, small windows and keyboard dismissal. Closing/reopening does not restore a capture, and sessions/locks JSON export does not include it.

## Safe SQL file handling

The renderer keeps each buffer in its existing workspace tab. A separate main-process registry (`sql-files.json` in the application data directory) associates tab IDs with canonical paths, saved-content hashes, disk revisions, BOM/newline choices and up to 20 recent paths. SQL text remains in the existing workspace recovery store; the file registry contains no SQL or credentials. File paths and workspace SQL are local, unencrypted data. No workspace schema migration is needed; old scratch tabs continue to work. A damaged registry produces a notice and leaves recovered SQL intact for Save As.

- Open uses a native dialog or an opaque recent-file ID. The renderer cannot supply arbitrary filesystem paths. Already-open files focus their owning tab, including when its buffer is dirty; new files create disconnected tabs. Connecting an associated tab does not replace file text with an engine starter query.
- Save uses the owning tab's captured SQL and registered path. Save As uses a native dialog, preserves the old file and changes the association only after success. Saving into a file associated with another tab is refused. Generated definition/schema/query-builder exports remain standalone exports and cannot overwrite another tab's file.
- Dirty indicators compare normalized-newline SHA-256 hashes. Normalizing CRLF in Monaco does not create a false edit. The path/status strip distinguishes workspace recovery from disk saves. File actions leave sessions, results and transaction guards intact.
- Closing a tab explicitly chooses keep, save-and-close, or discard. Cancellation and failed saves leave it open. Quit first flushes recovery, then offers keep working, quit retaining buffers, or save all edited file tabs. Failed/cancelled writes keep the application open. Transaction and staged-grid-edit guards still apply. Recovery never reconnects or replays SQL.
- Focus and three-second checks detect changed, missing and unreadable files. Fingerprints include content and filesystem identity/timestamps, so atomic replacement with identical SQL is still visible. Nothing reloads automatically. Reload confirms discarding local edits; Save confirms replacement of external edits and revalidates the reviewed revision. Deleted files require Save As.
- Reads validate regular UTF-8 text, reject NULs and enforce byte/character bounds. Writes preserve a loaded UTF-8 BOM and LF/CRLF convention, fsync an adjacent temporary file, recheck the destination and atomically rename it. New files use exclusive creation through a temporary-file link. Temporary files are cleaned up after failure. Existing Unix mode bits are retained; symlink destinations and hardlinked writes are refused. Open resolves a selected symlink once and displays its canonical target.

Limits: 1,000,000 UTF-16 code units per SQL file, 20 tabs, 5,000,000 workspace SQL code units and 20 recent paths. Uniform line endings are written using the loaded file's convention. SQL files are never saved automatically; recovery is separate. Atomic replacement and revision checks do not provide cross-process locking: another program can still write in the narrow final check/rename window, and network filesystems can have different durability guarantees. ACLs, extended attributes and file ownership are not promised across replacement. OS file-manager association/drag-and-drop and non-UTF-8 conversion are not implemented.

## Snippet import and export

**Query library → Snippets** has actions for a saved entry or the currently listed snippets. The filtered list determines export membership; unsaved form edits are kept but excluded. The host captures saved content before opening the native save dialog. Exports publish a completed, flushed private temporary file using exclusive hard-link creation beside the destination. Existing files and symlinks are refused, and temporary files are cleaned up. Filesystems without hard-link support fail without publishing a partial destination; there is no overwrite fallback.

The portable UTF-8 JSON format is strict and versioned:

```json
{
  "format": "dbcommander-snippets",
  "version": 1,
  "snippets": [
    {
      "name": "Customer lookup",
      "description": "Find a customer by ID",
      "engine": "postgres",
      "sql": "SELECT * FROM customers WHERE id = :id",
      "favorite": true
    }
  ]
}
```

`engine` is optional (any engine); other snippet fields are required. Local IDs, timestamps, connections, parameter values and history are not accepted as extra fields. SQL is a template, not a value-binding record; literal SQL text remains readable. The existing snippet schema trims outer SQL/name whitespace while preserving the SQL body, Unicode, comments and portable parameters. Standalone SQL files and other IDE snippet formats are not imported through this format.

Main-process file reads use an opened regular-file descriptor with a 32 MiB bound and strict UTF-8 decoding (BOM accepted). File growth during reading, invalid JSON, unsupported versions/engines/fields, empty libraries and invalid entries fail before a review is issued. A document has at most 200 entries and 5,000,000 SQL characters, with 100,000 characters per template. The same limits apply when combined with the existing saved library.

The utility process retains one captured review for ten minutes. The renderer receives a review ID and cannot replace its SQL at confirmation. File edits after review do not change the captured import. Cancelling discards the review; successful use consumes it. Confirmation revalidates a hash of the saved snippet contents inside an SQLite transaction. Concurrent library edits, invalid selections, expiry, storage limits or write errors leave existing snippets intact; any earlier inserts in the batch roll back.

Duplicates use NFC-normalized, case-insensitive names within the same engine, including duplicates inside the selected file entries. Default **Skip duplicates** keeps the first selected new name. **Keep both with new names** uses bounded ` (imported N)` suffixes and never replaces existing entries. The same deterministic naming plan drives the preview and transaction. Imports create fresh local IDs/timestamps and preserve engine, favorite and description. No profile, history, query buffer, fetched results or database transaction is modified, and no SQL executes automatically.

## Decimal, date and timestamp parameters

The shared strict parameter schema accepts three additional types without changing the IPC shape or workspace schema. All validation applies to query execution, full-result export and EXPLAIN. The prompt shows format guidance next to the selected type; changing a type clears a previous validation error. Cancel runs nothing, reopening requests fresh values, and parameter values never become recovery state, snippet contents, job metadata or history values.

- Decimal uses plain signed base-ten text, at most 38 digits of precision and 30 fractional digits. The optional sign is `-`; exponent notation, grouping, whitespace, leading `+`, unnecessary leading zeros and incomplete fractions are rejected. Precision/scale come from validated string lengths, retaining fractional zeros; the value never passes through a JavaScript Number. These portable bounds fit SQL Server/DuckDB/Oracle precision and [MySQL scale](https://dev.mysql.com/doc/refman/8.4/en/precision-math-decimal-characteristics.html).
- Date uses a strictly validated Gregorian `YYYY-MM-DD`, years 1000–9999. Leap years and month lengths are checked without Date parsing. The common range follows the [MySQL DATE/DATETIME range](https://dev.mysql.com/doc/refman/8.4/en/datetime.html).
- Timestamp accepts a space or `T` separator, seconds and an optional one-to-six-digit fraction. Transport normalizes the separator to a space and pads the fraction to six digits. It is a calendar value without a timezone: offsets/`Z`, leap seconds, invalid hours and extra precision are refused. No local/UTC conversion or millisecond rounding takes place.

| Engine | Decimal | Date | Timestamp |
| --- | --- | --- | --- |
| PostgreSQL | Bound string → DECIMAL(p,s) | DATE | TIMESTAMP(6) WITHOUT TIME ZONE |
| MySQL / MariaDB | Bound string → DECIMAL(p,s) | DATE | DATETIME(6) |
| SQL Server / Azure SQL | TDS NVARCHAR → DECIMAL(p,s) | CONVERT(DATE, bind, 23) | CONVERT(DATETIME2(6), bind, 121) |
| Oracle | Explicit TO_NUMBER format and decimal separator → NUMBER(p,s) | TO_DATE with FXYYYY-MM-DD, Gregorian calendar | TO_TIMESTAMP with FXYYYY-MM-DD HH24:MI:SS.FF6, Gregorian calendar |
| DuckDB | Bound VARCHAR → DECIMAL(p,s) | DATE | TIMESTAMP (microseconds) |
| SQLite | Bound TEXT | Bound TEXT | Bound TEXT with six fractional digits |

SQL contains generated type/format declarations and placeholders, never the supplied value. Oracle decimal parsing uses explicit `NLS_NUMERIC_CHARACTERS` so changing the session's decimal separator does not change the input value ([TO_NUMBER](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/TO_NUMBER.html)); temporal formats and the Gregorian calendar are explicit as well, including when the session uses a non-Gregorian calendar ([Oracle calendar conversion guidance](https://asktom.oracle.com/ords/asktom.search?tag=ethiopian-calendar-support)). SQL Server uses explicit [CONVERT styles](https://learn.microsoft.com/en-us/sql/t-sql/functions/cast-and-convert-transact-sql). DuckDB uses its existing string binding for the new types, avoiding native floating-point/Date conversion. Private Oracle/SQL Server plan connections use the same conversion path.

The destination column and subsequent SQL expressions retain native semantics: a narrower decimal/temporal type can round, truncate or reject values, and assigning a timezone-free value to a timezone-aware column uses engine/session rules. SQLite has no native exact decimal/date type; TEXT retains the bound representation, while [numeric affinity and arithmetic can coerce it to floating point](https://www.sqlite.org/datatype3.html). The prompt explains this when a new type is selected on SQLite. Numeric formatting, trailing zeros and Oracle's DATE midnight/extra timestamp display digits remain engine-specific. Timezone-aware instants are supported by the later [timezone parameter milestone](#timezone-aware-timestamp-parameters); the timezone-free Timestamp type remains unchanged.

## Timezone-aware timestamp parameters

`shared/parameters.ts` adds `timestamptz` to the existing strict parameter schema. The shared renderer prompt labels it **timestamp with timezone** and supplies engine-specific storage guidance. Execution, export and EXPLAIN validate the same schema in the host before reserving sessions or creating jobs. No IPC or workspace version change is required; persisted history continues to contain parameter names/types only.

Input is a Gregorian timestamp with a space or `T` separator, required seconds, optional one-to-six-digit fraction, and required `Z` or `±HH:MM`. Offsets range from -14:00 through +14:00 (14 hours requires zero minutes). Unknown `-00:00`, IANA region names, whitespace, leap seconds, invalid dates, missing offsets and extra precision are rejected. Local and normalized UTC dates must both fit years 1000–9999. Users supply the offset applicable to their instant, including either side of a daylight-saving overlap.

`timestampTzValue` adjusts integral calendar minutes and at most one calendar day, handling leap years and month/year boundaries. Fractional digits remain text; the production path never uses JavaScript Date or floating-point seconds. Every driver binds canonical `YYYY-MM-DDTHH:mm:ss.ffffff+00:00` as a string, then applies a fixed engine conversion. The instant is retained; the original offset is deliberately discarded. For example, `2026-10-25T02:30:00.123456+02:00` binds the same instant as `2026-10-25T00:30:00.123456Z`, while the same local time with `+01:00` is one hour later.

| Engine | Bound conversion and semantics |
| --- | --- |
| PostgreSQL | TIMESTAMP(6) WITH TIME ZONE; native output follows session TimeZone. |
| SQL Server / Azure SQL | CONVERT(DATETIMEOFFSET(6), bind, 127), with explicit ISO offset. |
| Oracle | Parse the normalized UTC calendar portion with TO_TIMESTAMP and explicit Gregorian format, then FROM_TZ(..., '+00:00'). This also works on isolated plan connections and non-Gregorian sessions. |
| DuckDB | TIMESTAMPTZ; no extension installation or network access required for fixed-offset input. Native Neo result strings use the process timezone offset captured when the client loads. |
| MySQL / MariaDB | Extract the UTC calendar portion and cast to DATETIME(6). This value has no native timezone. |
| SQLite | Canonical UTC TEXT, including six fractional digits and +00:00. |

[PostgreSQL](https://www.postgresql.org/docs/current/datatype-datetime.html) and [DuckDB](https://duckdb.org/docs/current/sql/data_types/timestamp) represent timezone timestamps as instants rather than preserving the original zone. [SQL Server DATETIMEOFFSET](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetimeoffset-transact-sql) accepts explicit ISO offsets independently of session date-format settings. Db Commander consistently normalizes to UTC even on engines that can retain offsets. Oracle uses [FROM_TZ](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/FROM_TZ.html) after the same explicit calendar parsing used for timezone-free timestamps.

Destination columns and subsequent SQL retain native semantics. In particular, [MySQL TIMESTAMP storage converts from the session timezone to UTC](https://dev.mysql.com/doc/refman/8.4/en/datetime.html); assigning this UTC DATETIME value to TIMESTAMP requires a UTC session or an explicit conversion. The prompt explains that requirement, and MySQL/MariaDB contracts demonstrate both non-UTC and UTC assignments. SQLite TEXT retains the representation; SQLite date functions or other column affinities can change precision/representation. Narrower target precision can round values on any engine. Named timezones, DST lookup, nanoseconds, OUT parameters and parameterized scripts remain outside this milestone. Typed arrays are supported by the later array milestone below.

## Array query parameters

The existing `{name,type,value}` IPC shape now accepts `text[]`, `integer[]`, `decimal[]`, `date[]`, `timestamp[]`, `timestamptz[]`, `boolean[]` and `hex[]`. Value is a one-dimensional JSON array, parsed after checking its character limit. Non-NULL values must be JSON strings, except `boolean[]` accepts JSON booleans. JSON numbers are rejected even when they appear small: parsing can already round fractional lexemes into integers. Every element is checked by the existing scalar validator, and errors identify the element index without echoing its contents. Integer and hex validation now also reject trailing whitespace/newlines.

The prompt groups scalar/array types, explains the format, limits, NULL and empty-list behavior, and preserves engine-specific temporal/SQLite precision guidance. Changing types never silently inserts an empty array. Each run, export or plan requests fresh values; cancellation retains the previous result. Parameter values are not added to history, snippets, transfer metadata or workspace recovery. Plans and explicitly exported result data can contain them.

### Compilation and engine behavior

The lexical compiler recognizes an array marker as the only code item inside `IN (:items)` / `NOT IN (:items)`, allowing comments around the marker. It emits individual native scalar binds with the existing exact numeric/temporal/binary conversions. Mixed lists such as `IN (:items, 1)` are refused. Empty arrays emit a typed zero-row subquery (`FROM dual` on Oracle), preserving empty-set semantics even for a NULL left operand. NULL elements are bound NULLs; `[null]` is not an empty array. Native SQL collation, equality, NULL and target-column rules continue to apply.

Outside that portable form, PostgreSQL emits an explicitly typed `ARRAY[...]` constructor and DuckDB emits an explicitly typed `[...]` LIST constructor. Elements still use native scalar binds, so integer limits, microseconds, UTC normalization, binary bytes, duplicate values and ordering are retained without serializing engine array literals. Empty/all-NULL constructors carry an explicit element type. PostgreSQL/DuckDB support ANY, unnest and assignments to compatible native columns. Other engines reject array expressions outside IN/NOT IN before acquiring an operation. SQL Server table-valued parameters, Oracle named collections, multidimensional arrays and fixed-length DuckDB ARRAY types are not exposed by this prompt.

Decimal arrays derive a common precision and scale from the maximum integral digits and fractional digits. All elements and the native container use that common type; combinations requiring more than 38 digits are rejected instead of rounded. The 30-fractional-digit limit remains. SQLite uses TEXT and retains each original decimal string. Existing MySQL UTC-DATETIME and Oracle explicit NLS-independent temporal/numeric conversions apply to every element.

Limits remain 100 distinct names, 1,000 marker occurrences, 65,536 characters per value and 262,144 aggregate value characters. Added limits are 1,000 elements per array and 1,000 emitted scalar bindings per statement, including repeated arrays and ordinary parameters. Expansion never escapes this budget. Empty arrays emit zero binds but remain parameterized requests for preflight, execution and diagnostic privacy. The scalar transport refuses uncompiled array values defensively.

Semantics follow [PostgreSQL array constructors](https://www.postgresql.org/docs/current/sql-expressions.html), [PostgreSQL IN/ANY/NULL behavior](https://www.postgresql.org/docs/current/functions-comparisons.html) and [DuckDB LIST types](https://duckdb.org/docs/current/sql/data_types/list). No dependency, workspace-format, pipeline or release-policy change is required.

## D1: broader safe table editing

The database host generates SQL preview and execution from the same parameterized statement builder. A preview shows statements and bound-value counts without exposing values or starting a transaction; Apply separately retains the existing table-definition check, locked comparison against host-owned original values, one-row effect checks and all-or-nothing rollback. PostgreSQL assignments let the target enforce length rather than explicitly casting to a narrower type, which could silently truncate data. MySQL/MariaDB still refuse visible trigger tables and non-InnoDB or temporary targets; other unsupported columns still block the entire editor rather than weakening original-row comparison.

The renderer stages duplication and bounded rectangular TSV paste without modifying protected keys or generated cells. A full-value dialog supports multiline text and JSON, plus hex-encoded PostgreSQL `bytea` and DuckDB `BLOB` non-key columns. Original values and staged changes remain bounded: 8 MiB each, 200 staged rows and at most 262,144 characters per value; the per-value read bound decreases for wide pages so the maximum aggregate database projection does not grow. SQLite text containing NUL is refused for editing because SQLite's text substring would otherwise hide the remainder. SQL Server checks session `TEXTSIZE` before opening and applying so truncated reads cannot masquerade as complete originals. Binary values remain excluded from data comparison and file import.

A conservative lexer recognizes only one fully qualified `SELECT * FROM schema.table` (and DuckDB's catalog-qualified equivalent), matched uniquely against loaded table metadata. The user explicitly opens a fresh table page; the original query is not replayed, its captured rows do not become authoritative originals, and the page can differ from the result. Joins, filters, projections, comments and other forms remain read-only. The existing session, transaction, protected-profile and table eligibility gates still apply.

Local validation includes 1,089 unit tests with three platform skips, all 95 SQLite/DuckDB Docker contracts, and the focused grid contract on PostgreSQL, MySQL, MariaDB, SQL Server/Azure profile, SQLite, DuckDB and Oracle. SQL Server ran under x64 emulation on the ARM Mac; live Azure remains unqualified. Native Mac checks cover the new editing workflows, existing grid/selection/screen-reader regressions and an unsigned packaged build. Cross-platform CI and release qualification remain separate.

## D2 transfer workflows — 30 October 2026

D2 extends the existing streaming transfer owner instead of introducing a second execution path. JSON Lines wraps bounded physical records into the strict JSON parser, so malformed UTF-8, non-string scalar cells, duplicate names, width/cell limits, NUL and surrogate validation remain shared. File inspection opens one no-follow descriptor and previews at most ten rows. The import fingerprint still binds the path, file identity, headers and live target definition; insert/validation/rollback remains in TableEditor.

Transfer mappings are strict metadata-only records in a lazy workspace table, capped at 50 and updated atomically. Compatibility compares engine, exact ordered source headers and destination names/types. Neither rows, paths, SQL nor secrets enter mapping persistence. The UI reuses the S1 prepare/apply plan for inferred-table creation, revalidating reviewed SQL and engine transaction rules. Table creation is separate from import, with an explicit empty-table commit where required. Non-identifier or case-colliding file headers receive unique editable column suggestions instead of failing during render. Conservative suggestions never infer NOT NULL and avoid leading-zero conversion, out-of-range integers and SQLite decimal affinity.

Database copy has two explicit steps. Capture reserves source and destination through the registry operation owner before work starts; it runs the reviewed query once through fullExport and writes a private JSON file in a mode-0700 temporary directory (file mode 0600). Only complete, successful source execution is published for mapping review. A target import preview binds that file and live schema. Capture metadata exposes source/destination IDs, total rows, ten sample rows, expiry and a host-generated ID; no renderer-supplied path is accepted for copy. At most two active/retained captures exist, each expires after ten minutes. Consuming a capture removes its replay authority before scheduling writes; import uses the existing signature validation, native transaction, parameterized inserts and whole-batch rollback. Normal shutdown, discard, expiry and consumption remove private files. Abrupt failure can leave OS-temp data but never recoverable replay authority.

Transfer progress and authoritative terminal session states cover both physical owners. A later capture-review-only update cannot overwrite newer transaction or operation state. Staged edits and shared-tab ownership still block the renderer, and registry reservations, autocommit/transaction guards and write protection remain authoritative at IPC. Source parameters are validated/bound once and diagnostics remain redacted. Capture is not a distributed transaction: source consistency is the source SELECT's engine behavior; target conversions, constraints and Oracle empty-string semantics still apply. Partial/unknown settlement is reported rather than retried.


## Guided backup and restore — 30 October 2026

The existing backup job owner remains the execution authority. A separate advisory inspection reserves the same physical session operation and checks bounded file headers, destination absence/write access, native tool identity/version and engine metadata without creating artifacts, databases, schemas or Data Pump jobs. PostgreSQL archive listing and server versions, MySQL-family branded dumps and visible target conflicts, SQL Server file lists, Oracle DIRECTORY/dump metadata and Azure source state are reported at their actual scope. Execution repeats its original validations; a green inspection grants no write authority or integrity guarantee. Diagnostics redact connection secrets and permissions that cannot be established read-only remain explicit review notes.

The renderer extends the incumbent modal with configure, check/review and run/result states. Native local-file and tools-folder selectors keep only bounded per-engine/purpose directories in application settings, with serialized updates preserving concurrent preference/tray changes. SQL Server paths and Oracle DIRECTORY files stay server-side; Azure remains a billed database copy. A pending picker prevents review of stale input. Input changes reset review and restore trust. Job history adds search/status filters, timing, phases, diagnostics and truthful partial/unknown outcome guidance without replay or automatic cleanup.

Completed local jobs can reveal their trusted journal paths through the main process. Connecting a successful restore requires the still-open original session, retains its protected connection configuration in main-process memory and creates an independent empty query tab without associating it with the source saved profile or replaying SQL. Embedded targets open read-write without a create fallback. Oracle schema-only accounts instead receive explicit manual connection guidance. Existing tab limits, recovery/file/close readiness, transaction, backup and session guards remain in force. See [workflow guidance](BACKUP_RESTORE.md) and [qualification](DRIVER_TESTING.md#backup-and-restore).
