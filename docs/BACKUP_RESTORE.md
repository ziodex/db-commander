# Database backup and restore

Right-click the current database in the sidebar and choose **Database backup and restore**. Shift+F10 opens the same menu from a focused database. Select another database before backing it up; switching safeguards remain in force. **Commands → Database backup and restore** also opens recent jobs when disconnected. Choose the operation and artifact, review the server, source, destination and scope, then explicitly confirm. Restore creates a new database, schema or file. There is no overwrite, `REPLACE`, cleanup or automatic retry option. Other tabs remain usable; the owning tab cannot run SQL, edit tables, switch databases or disconnect during its job. Commit/rollback first; MySQL/T-SQL manual commit mode must also be disabled. Oracle's normal manual commit mode is supported when its transaction is idle.

The dialog shows recent jobs and bounded diagnostics across tabs. Closing the dialog leaves the job running. **Cancel job** requests cancellation and waits for the engine's response. Quit asks separately about unfinished backup jobs. Local job metadata is saved in `backup-jobs.json`; jobs interrupted by an application/host crash are marked **unknown**, never resumed or replayed. A failed or cancelled server restore can leave a partial target, and a disconnected server job may continue. Inspect the server and target before retrying.

| Engine | Backup and restore implementation | Location and requirements |
| --- | --- | --- |
| PostgreSQL | Compressed custom archive from `pg_dump`; `pg_restore` into a newly created database in one transaction, without source ownership/ACLs | Local file. Install the client tools matching the server major version; PATH or an explicit tools directory. Database creation privileges are needed for restore. Source roles, tablespaces and cluster settings are outside this backup. |
| MySQL | `mysqldump`, then the `mysql` client into a new database | Local SQL file with an engine/version header. Matching major version tools. Includes triggers, routines and events. Full online backup requires InnoDB tables; avoid concurrent DDL. Users/grants are not exported. |
| MariaDB | `mariadb-dump`, then the `mariadb` client | Same workflow as MySQL, using MariaDB tools and MariaDB artifacts. Their formats/client commands are checked separately. |
| SQL Server | Full `COPY_ONLY` native backup with checksums; `RESTORE VERIFYONLY` and `RESTORE DATABASE` to a new name | **Server-side** `.bak` path accessible to the SQL Server service account. Restore moves ordinary data/log files to unique names in the instance's default directories. Requires backup/restore and metadata/file-check privileges. FILESTREAM/special filegroups, striped/encrypted media and instance-level recovery need administration tools. |
| Azure SQL Database | Independent, consistent recovery database copy; restore makes another copy from it on the same logical server | **Cloud database names**, not files. Requires access/creation rights in `master`. Each copy is a separately billed database. Cancellation stops monitoring and reports an unknown outcome; it does not delete cloud databases. This does not implement BACPAC, point-in-time recovery, geo-restore or `.bak` import. |
| Oracle | Native `DBMS_DATAPUMP` schema export and import with schema remapping; full exports use a flashback SCN | **Server-side** Oracle DIRECTORY object and simple `.dmp` filename. Requires directory access and Data Pump privileges; creating the restore schema also requires CREATE USER and quota privileges. New schemas have no authentication credential. Server logs identify the job and errors. This is schema recovery, not RMAN or a full CDB/PDB backup. |
| SQLite | Native online backup API; integrity-checked restore into a new file | Local `.sqlite` snapshot, including committed WAL content. Supports file and in-memory source databases. Only `main` is included; no temporary/attached databases. |
| DuckDB | Native Parquet export/import produces a single new DuckDB file; native catalog copy for schema-only backups | Local `.duckdb` snapshot. Includes tables, constraints, views, indexes, sequences and macros in the selected catalog. Temporary export space is required in the destination directory. Other attached catalogs and temporary objects are excluded. |

Schema-only backups are available for PostgreSQL, MySQL, MariaDB, Oracle and DuckDB. Full backups are the default. Local artifacts are built in a private sibling directory and published only after completion using an exclusive link; existing files, including symlinks, are refused. The destination filesystem must support hard links. Server-side failures may leave dump files, logs or stopped jobs to inspect and remove with the engine's administration tools.

Native tools are not bundled or downloaded. Install them separately and set **Native tools directory** if the desktop application's PATH does not include them. PostgreSQL uses a private password file; MySQL/MariaDB use a private options file with login-file overrides disabled where supported. Passwords/tokens are never arguments, job records or manifests. TLS follows the selected connection. Temporary credential files are removed after normal completion/failure/cancellation; an OS crash or forced kill can leave private temporary directories that the OS/user must remove. Artifacts themselves contain sensitive data and are not encrypted by Db Commander.

Restore only trusted backups: native SQL, routines, triggers and views can execute with your privileges. A new target protects against Db Commander's own overwrite operations; it is not a sandbox for SQL contained in an archive. Explicit database/schema references and external dependencies in views or routines may still refer to the original environment after a rename. Oracle Data Pump does not rewrite all embedded references; compilation/import errors are reported as failures, with partial objects retained for inspection. Validate application queries, dependencies, grants and constraints before promoting a restored database.

Current follow-up scope: selected-object/data-only jobs, selectable compression/parallelism, external archive inspection, restore into an existing target, cross-server Azure copies, BACPAC and managed recovery, scheduled backups, retention and encrypted artifact storage. These are not silently approximated by CSV export.

## Native format references

PostgreSQL archives and version/restore semantics follow [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) and [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html). MariaDB artifacts use [mariadb-dump](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump). Azure's separate workflow follows [database copy](https://learn.microsoft.com/en-us/azure/azure-sql/database/database-copy?view=azuresql); SQL Server files use [RESTORE](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-transact-sql?view=sql-server-ver17). Oracle uses the [Data Pump API](https://docs.oracle.com/en/database/oracle/oracle-database/26/arpls/DBMS_DATAPUMP.html), including the documented [schema remapping limitations](https://docs.oracle.com/en/database/oracle/oracle-database/21/sutil/oracle-datapump-import-utility.html). Embedded engines use [SQLite backup](https://nodejs.org/download/release/latest-jod/docs/api/sqlite.html) and DuckDB's [native database copy](https://duckdb.org/docs/current/sql/statements/copy) / export-import formats.
